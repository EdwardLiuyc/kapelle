# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Use plain language, short sentences, and avoid dense or overly compressed phrasing.

## What this is

`kapelle` — a minimal [Agent Client Protocol](https://agentclientprotocol.com) **client** in TypeScript and ES modules. One runtime dependency (`marked`, presentation only — see `core/markdown.ts`), Node ≥24, `"type": "module"`, no build step; `biome` formats and lints (`npm run fmt:check`), `node:test` covers pure functions and wire behaviour (`npm run test`).

The inversion that governs every design choice: **this code is the client, the coding harness is the agent.** We spawn the harness as a subprocess, own the workspace, serve its filesystem requests, and decide its permissions. Harnesses (opencode, gemini, copilot, …) authenticate themselves — this client never touches a key.

## Commands

```bash
npm run check               # type-check: tsc --noEmit, guarded on .ts discovery (protocol/ is typed since M1a-2)
npm run fmt                 # biome format + lint autofix (biome check --write .)
npm run fmt:check           # biome format + lint check (biome check .)
npm run test                # node:test: pure functions, plus wire behaviour in protocol/
npm run knip                # dead-code / unused-export check, both dev and --production
npm run selftest            # end-to-end against mock-agent.mjs, --mode auto (writes ACP_TEST.md)
npm run test:harness        # opt-in: the real harnesses, local only (needs credentials, spends tokens)
node cli.ts "self test" --cmd "node mock-agent.mjs" --mode safe   # same run, write refused
node cli.ts "<prompt>" [--agent opencode|omp|pi|claude|gemini|copilot] [--cmd "<cmd>"] [--cwd dir] [--mode ask|safe|auto] [--verbose] [--quiet]
node cli.ts --file <run.json>   # N tasks from a run file (tasks.json is the worked example)
node daemon.ts [--port n] [--permission-timeout s]   # one HTTP daemon for all repos (M2-1); port, pid and token in $XDG_RUNTIME_DIR/kapelle/daemon.json
node cli.ts daemon start [--port n] [--permission-timeout s]   # the same daemon, in the foreground; ^C or SIGTERM cancels runs and exits (M2-4)
node cli.ts daemon add <path>         # POST /repos to the running daemon, token read from daemon.json
```

`node:test` covers pure functions in `core/` and `protocol/`, and — per the 2026-08-31 amendment in `docs/STORIES.md` (M1a-1) — behaviour whose subject *is* the wire, which a pure function cannot express. Suites live in a `tests/` folder beside their sources — `core/tests/`, `protocol/tests/`, and `tests/` at the root for `cli.ts` and `render.ts`; `npm run test` runs them all. `protocol/tests/agent.test.ts` is subprocess-driven: it spawns **fake** harnesses — `node -e "…"` scripts written inline in the test file, plus `mock-agent.mjs` where a scenario already covers the case — over real stdio, to prove what does and does not reach the subprocess. No real harness binary is launched by `npm run test`, which is why CI needs no credentials; that suite is `integration/` below. `mock-agent.mjs` is the end-to-end test harness: it implements the agent side of the protocol and drives every client code path (streaming, `fs/read_text_file`, `session/request_permission`, `fs/write_text_file`). **Verify changes to `protocol/agent.ts` against it before touching a real harness** — it needs nothing installed. Extend `mock-agent.mjs` when adding client capabilities so the new path is exercisable offline. Its scenario fixtures are selected by `--scenario <name>` on argv (M1b-5) — `refuse`, `silent-session`, one per `core/result.ts` cross-check, M1c-2's two watchdog fixtures (`stall`, `repeat`), and `remember`, which answers each turn with the previous turn's prompt so a test can tell a session that kept its context from a new one — never by a keyword in the prompt, because `silent-session` fires during the handshake, before any prompt exists. An unknown name exits 2 rather than running the default path. `hostile-agent.mjs` (M1b-6) is its opposite and lives beside it: one attack per `--scenario` — path escape, absolute path, symlink escape, a write with no permission request, an allow-only permission menu followed by two writes, a non-JSON line, a line past the length cap, and a method we do not implement. It has **no default scenario** (a bare run exits 2), because a hostile agent with no attack selected is a worse mock, and `protocol/tests/hostile.test.ts` drives every one of them. Every scenario ends its turn normally after the attack: the story's *Done when* is refused **and the run continues**, so a scenario that killed the turn would prove only half of it. `ACP_TEST.md` in the repo root is selftest output, not source; deleting it is safe.

`tests/cli.test.ts` drives `cli.ts` as a real subprocess and needs **no harness** — argv validation, the notice/`--quiet` split, and the run-file path's concurrency all run against `mock-agent.mjs` or fail before a subprocess starts, so it runs in CI on every push. It shares `runCli` (which wraps `spawnCli`), the temp-dir helper, `gitRepo`, and `MOCK_AGENT` with the suite below rather than copying them. `tests/daemon.test.ts` is the same shape for `daemon.ts`: `spawnCli` with `daemon.ts` as the script and `--port 0`, a temp dir as each daemon's own `XDG_RUNTIME_DIR` (so no test meets another's `daemon.json`, or the developer's real one), the token read back from that file, and every route driven over real HTTP against `mock-agent.mjs`.

`integration/*.itest.ts` is the **real-harness** suite (`npm run test:harness`) — it drives `cli.ts` as a subprocess against the actual `opencode`, `claude-agent-acp`, `copilot` and `pi-acp` binaries, so it needs credentials and spends tokens. `node --test` does not discover the `.itest.ts` suffix, which is the only thing keeping it out of CI; do not rename the files. A harness that is not installed **skips** rather than fails, so a partial machine stays green. Assert on what the client controls — an exit code, our own notice lines — and **never on the agent's prose**, which changes every run. A file on disk is never enough on its own — an empty workspace is also what a harness that simply obeyed its negotiated plan mode leaves behind — so assert the client's own `_client_permission` refusal line first, then the directory. Measured 2026-09-04, three runs each: copilot requests an `edit` and `safePolicy` denies it; **claude never gets that far**, asking instead to leave plan mode (`switch_mode`), which `safePolicy` also denies — so `safe` there is an interlock, negotiate plan then refuse the way back out. opencode denies nothing because it asks nothing, so plan mode is an instruction the model may ignore — it wrote the file on one run out of several, which is why its tests assert the negotiation and the notice instead of the disk. pi-acp (measured 2026-09-09) also never asks permission and writes under `safe`; its ACP modes are thinking-effort levels, so it has no safety mode to negotiate and its tests assert the two notices instead of the disk. One helper, `twoTurns`, drives `AcpAgent` instead of `cli.ts`, because the CLI sends one prompt per session: it sends a second prompt only after the first turn ends and asserts both `end_turn`s, an unchanged session id and one spawn — measured passing on all four harnesses (`docs/M0-FINDINGS.md` §Multi-turn). `--mode ask` is untestable here at all: a test runner has no TTY, so it re-resolves to `safe` before the first notice is composed.

`--mode ask` requires a TTY and degrades to `safe` otherwise, so piped/CI invocations never block on a prompt.

**Package identity (M1c-5).** The package is `kapelle` and its `bin` is `{"kapelle": "./cli.ts"}`, so `npm link` puts `kapelle` on the PATH and `kapelle merge <runId>` works from anywhere; `node cli.ts` is the same entry point without the link, and is what this file's command block uses. **Do not "restore" the name the plan originally specified** — npm `agent-team@0.2.0` is a live, unrelated package of the same stated purpose that already claims both that package name and that `bin`, so taking it collides on the command a user types. `private: true` **stays**: it blocks `npm publish` only, never `bin` and never `npm link`, and nothing here is ready to publish. The name reaches the disk as well as the command, each with exactly one definition — `STATE_DIR` (`core/worktree.ts:42`) is `.kapelle`, `BRANCH_PREFIX` (`core/ids.ts:73`) is `kapelle`, `SECRET_PREFIX` (`protocol/registry.ts:96`) is `KAPELLE_`, and the per-task commit subject is `kapelle: <taskId> (<runId>)`, which has to match the branch it lands on. The schema `$id` is the exception: it is the repository's URL, so it tracks the repository name rather than the tool's. `"os": ["darwin", "linux"]` is the whole of the Windows block: `npm install` there fails with `EBADPLATFORM` (measured 2026-09-10; `--force` still bypasses it, deliberately un-closed). WSL is Linux.

The containment notice `warningsFor` prints, plus the not-negotiated line, are **never suppressed by `--quiet`** (#13): `safe` keeps its name only because that notice carries the caveat. `warningsFor` returns `{kind, text, onceKey?}` so the call site can make that split — `containment` always prints, `unverified` and `version` are advisory and `--quiet` drops them. A third line joins them under `--quiet`: M1b-4's cross-check disagreements, printed by a bus subscriber `cli.ts` installs **only** in the quiet path, because a quiet run has no task card to carry them. `onceKey` is the other half of that rule — a line that names a property of the *harness* rather than of one task prints once per run, which is why N opencode tasks say "never asks permission" once instead of N times.

**Harness spawn failures surface as opaque JSON-RPC errors** — typically `Internal error (code -32603)` on `session/new`, with the real message only on the harness's stderr under `--verbose`. Reach for `--verbose` first — or, for a `--file` run, read `.kapelle/runs/<runId>/<taskId>.stderr.log`, which M1b-7 writes for every task with no flag asked for. The `--agent claude` case is the one to know: older adapters refused to start a nested session when they saw the markers a parent Claude Code session leaves in the environment, and `AcpAgent` passes its `env` through to the subprocess. The `claude` entry scrubs those markers (`CLAUDECODE`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_CODE_ENTRYPOINT`) via the registry `env` field (`protocol/registry.ts`), so no `env -u ...` prefix is needed. Adapter 0.49.0 no longer refuses, and 0.75.1 still does not — re-checked 2026-09-09 with all three markers set and the scrub bypassed — so the scrub is regression insurance rather than a fix for a live failure. The deprecated `claude-code-acp` adapter is no longer in the registry.

## Architecture

One direction of dependency: `cli.ts` and `daemon.ts` → `core/` → `protocol/agent.ts` + `protocol/registry.ts` + `render.ts`, typed by `protocol/types.ts`. The one arrow that points the other way is `render.ts` → `core/markdown.ts` (M1c-7): the parser is shared with M4's dashboard, so it lives in `core/` and the paint stays per surface. **`core/` may import `protocol/`; never the reverse** — that is why `AcpAgent`'s default policy refuses everything rather than being `safePolicy`.

- **`protocol/agent.ts`** — everything protocol. An inbound stdout line longer than `MAX_LINE_LENGTH` (32 MiB, M1b-6) is dropped with a line on stderr that `--quiet` does not suppress, and the turn carries on; `readline` has already buffered it by then, so that refuses the payload rather than bounding the memory — a real bound means a manual chunk scanner, marked `ponytail:` at the constant. `AcpAgent` owns one subprocess: spawn, newline-delimited JSON-RPC over stdio, `initialize` handshake (hard-fails on `protocolVersion` mismatch), `session/new`, `session/prompt`, `session/cancel`. **`stop()` closes stdin first and SIGKILLs only a harness still alive after `stopGraceMs` (5 s), and resolves once it is gone** (M2-4): every measured harness runs its shell commands in a session of its own, so no signal from here reaches them, and SIGTERM left opencode's running command alive where end of file left nothing on all four (`docs/M0-FINDINGS.md` §M2-4). `core/run.ts` awaits it, so a task is not over while its harness can still write. It handles exactly three inbound requests — `fs/read_text_file`, `fs/write_text_file`, `session/request_permission` — and one notification, `session/update`, which it forwards to `onEvent`.
- **`protocol/registry.ts`** — the entire adapter layer (M1a-4, was `agents.mjs`). A map of agent id → `{launch, measured?}`. **The split is load-bearing.** `launch` is `{command, args, env?}` — a recipe we choose. `measured` is a lab report: `shell`, `argvChannel`, `asksPermission`, `modeMap?`, `usage`, `meta?` and `measuredOn`, every field a claim about one *build*. `omp` and `gemini` were never run here, so they carry no `measured` — its **absence is the only marker of an unverified harness**, and `warningsFor` reads that absence as the least contained harness we did measure. `pi` has a measured half since 2026-09-09, but its `modeMap` is omitted because its ACP session modes are thinking-effort levels, not safety modes. Supporting a new harness is still one entry, not an integration. `env` is `{unset?, set?}`, applied by `resolveEnv`, which also strips `KAPELLE_*` from every harness's environment unconditionally (M2-8's shared secret must never reach a subprocess). `resolveEnv` returns `process.env` **by identity** when there is nothing to do, so quirk-free harnesses don't each get a copy. `resolveAgent` also parses `--cmd` strings and derives a readable label (`node mock-agent.mjs` → `mock-agent`); a `--cmd` spec has no `measured` half, so it warns as unverified.
- **`render.ts`** — terminal formatting for `session/update`. Pure presentation; no protocol logic. **`agent_message_chunk` is drawn raw as it streams and repainted one markdown block at a time** (M1c-7): when `blockEnd` says a block has closed, the rows just drawn are erased and the rendered block replaces them. The repaint is skipped — raw printed, move on — when stdout is not a TTY, when `NO_COLOR` is set, or when the block is taller than the screen, so a piped run still reads as plain markdown source; those are the only escape hatches, no flag was added. Its state is module-level because the erase is only correct while **one** thing owns the cursor: `cli.ts:185` subscribes it on the single-agent path, and the `--file` path prints milestones instead. Making that state per-agent looks like the fix for multi-agent output and is not — it stops the corruption and leaves the result unreadable. `flushStream` is exported for the one thing `render` cannot see: the end of a turn, which `cli.ts` prints past.
- **`core/markdown.ts`** — the only file that knows a markdown library exists (M1c-7). `toAnsi(md, {width})` today; `toHtml` is one `marked.parse` line M4-1 adds when it has a consumer, and is left out until then because `npm run knip` fails on an export nobody imports. `blockEnd` is the pure half: a blank line closes a block, except inside a fence, and except in a **list**, which waits one line because `- a\n\n- b` is one loose list in CommonMark and splitting it restarts an ordered list's numbering. Nothing here wraps text — the terminal does that — so `width` reaches the table renderer alone. **`marked` was chosen at pickup over the story's own `md4x` recommendation, on measurement**: md4x 0.0.29 renders `- one\n  - alpha` as `* one  * alpha`. `earendil-works/pi` (MIT) makes the same `marked`-plus-own-paint choice and is credited in the file header for two shapes taken from it; its 1337-line terminal-string `utils.ts` is the tail we declined.
- **`core/run.ts`** — the pool and the status arithmetic (M1b-2). `statusFor` keys on the **triple** — `stopReason`, did we cancel, did the watchdog fire — because M0-4 measured copilot answering `end_turn` for a turn it had itself cancelled; our own record wins and `stopReason` is consulted only where the two agree. `runStatus` takes the worst task status, ordered `done < warned < cancelled < skipped < timed_out < failed`. **The roll-up is duration and turn count only** — `usage` stays on the task that produced it, tagged, never summed, because copilot counts cumulatively where opencode counts per turn. `taskCwd` is gone — M1b-3 replaced it with `core/worktree.ts`, acquired before the executor and released after, and teardown never changes a task's verdict. `runRun`'s third parameter is an injected executor, the only way to observe "never more than `maxConcurrency` live" without counting real subprocesses. **Each task now gets its own `AbortController`, chained to the run's** (M1c-1): the run-wide signal still cuts every task on ^C, but the watchdog's TTL cuts exactly one, and `statusFor` reads `watchdogFired` from this run's own record rather than from a `stopReason` M0-4 caught copilot lying about.
- **`core/worktree.ts`** — one `git worktree` per task at `.kapelle/wt/<runId>/<taskId>`, on branch `kapelle/<runId>/<taskId>` (M1b-3). `openWorktrees` preflights **once per run**, not per task: `.kapelle/` tracked or unignored, or a dirty tree, **throw** — the message carries the fix, and the preflight never edits `.gitignore` itself, because appending dirties the very tree it then refuses on. A cwd that *cannot* carry worktrees — not a repo, or no commit to branch from — **falls back** to the shared cwd with a notice instead, so the CLI's own suite keeps working in plain `mkdtemp` directories; that notice is containment-shaped and survives `--quiet`. **The tracked/unignored refusals run before the no-commit fallback** (M1b-7): `core/run.ts` writes `.kapelle/runs/` whichever way the preflight ends, so a fresh `git init` with no `.gitignore` entry throws rather than falling through and creating state that would be committed by accident. `release` is keyed on `TaskStatus`: `done`/`warned` commit the work and remove the checkout, everything below keeps it uncommitted for reading. A worktree that is **untouched** (no diff, HEAD still at the base sha) has its checkout removed; for a non-releasing status — the shape a harness that never started takes — the branch is rolled back too, while a `done`/`warned` task with an empty diff leaves its branch at the base ref without an empty commit. Three things `#85`'s review found, each with a test that is red without its fix: the dirty check is `--untracked-files=all`, never a bare `--porcelain`, which `status.showUntrackedFiles=no` silently empties — a task whose whole output was new files read as untouched and was removed with the work in it; `release` verifies the checkout is still on the task branch and **keeps it with a warning** when an agent moved HEAD, rather than committing onto a ref the run does not track; and a `--cwd` naming a subdirectory is re-entered at the *same* subdirectory inside the worktree, because returning the checkout root would widen `#guardPath` from the requested subtree to the whole repository. That prefix is `relative()` over **realpath'd** root and cwd: `--show-toplevel` resolves symlinks and `--cwd` does not, and subtracting one from the other produced a `..`-prefix that put one task inside another task's checkout. A containment check on the joined path backs it up. `kill -9` mid-spawn can still orphan one; that is M2-5's sweep. `openWorktrees` also returns the `root` it settled on, because M1b-7's per-task stderr logs live beside the worktrees under the same `.kapelle/` — in the no-repository fallback that root is the cwd, so a run outside a repository still leaves the logs — but a cwd that does not exist is never created for a log, since `mkdir -p` would turn a typo'd `--cwd` into a real empty workspace. `checkStateDir` is the repository half of that preflight — root, tracked, unignored, never the dirty tree — exported because the daemon runs it when a repository is added (M2-1).
- **`core/result.ts`** — the result contract (M1b-4). Three pure pieces: `RESULT_PREAMBLE`, appended to **every** prompt on both paths; `extractResult`, which takes the **last** `<task-result>` block in the message and returns `null` if the wrapper is absent or any of status/summary/details is blank after trimming (a missing *optional* field is `undefined`, never a rejection); and `crossCheck`, which compares the block against the task's changed paths and the permission count. It walks `<files>` **both ways** — `filesNotInDiff` for a claimed path the tree lacks, `filesUnclaimed` (M1c-6) for a changed path the list never names — but the second fires only where `<files>` is present and non-empty, because the field is optional and omitting it is what an agent that forgot looks like. Those paths come from `changedPaths` (`core/worktree.ts`), which reads `git status --porcelain -z --untracked-files=all`: **`-z` is load-bearing**, because without it git C-quotes unusual paths and writes a rename as `old -> new`, which needs a parser whose bugs #88 found. `crossCheck` is given the paths only when the task had a **worktree of its own** — in the shared-cwd fallback one task's files are in every other task's `git status`, and a task that touched nothing was told it had changed the tree without asking (measured 2026-09-08). **There is no re-ask** — `prompt()` throws while a turn is live (#62 R5), and a re-ask after `end_turn` is not sent either, because copilot's prompt handler aborts background work even on an idle session (github/copilot-cli#4555), so the preamble lands first time or the task carries `noResultBlock` and a summary synthesised from the tail of the prose, flagged as ours. Warnings are never fatal: `runOne` promotes `done` to `warned`, publishes each disagreement on the run bus as `_client_result_warning`, and touches nothing below it. `diff: undefined` is *unknown*, not *empty*, so a run outside a repository skips every tree-shaped check rather than warning on all of them; `policyNeverFired` does not fire where the registry already says `asksPermission: false`, because `warningsFor` marks that containment line with `onceKey` and the run prints it once per run.
- **`core/eventlog.ts`** — the event log (M2-2, #32). One bus listener per run, subscribed by `core/run.ts` before any task starts, appending every event **raw** to `.kapelle/runs/<runId>/events.jsonl` as `{seq, agent, update}` — `--file` runs included. **Chunks are never coalesced**: joined text cannot be split again, and a reader who wants messages joins them. **The file is the only replay source**: `follow(after, send, signal)` tails it from the reader's own offset, so history and live tail are one loop with no ring-to-file hand-off; memory is one byte offset per line. A line counts only once its write callback fires (`committed`), so no reader sees an unflushed or half line, and each commit rings the readers with the line itself — a reader waiting for exactly that `seq` sends it without touching the disk, and a reader still on the file never matches, because it reads to what was committed when it looked. That check and the send share one thread, which is why no worker thread was added: it would reintroduce the race, and the write already runs on libuv's pool. A log that cannot be written is a `run` notice and the run carries on. `send` has no backpressure (`ponytail:` at the interface).
- **`core/watchdog.ts`** — the stall detector (M1c-1). **One interval sweep for the whole run, not a timer per task.** Per-task limits and a single timer are not in tension: the sweep polls, so each task is compared against its own `stallIdleMs`/`stallRepeatCount`/`ttlMs`. A deadline timer per signal per task would have to be cleared and re-armed on every event, and M0-4 measured 443 events in one opencode turn. `sweepIntervalMs` derives the tick **once at run start** — a quarter of the finest non-zero time limit, clamped to 1 s–60 s — because a fixed tick would silently round a small `stallIdleMs` up to the next sweep; `stallRepeatCount` is a count, not a duration, and takes no part. **Idle and repeat only warn**; the task keeps running, and there is deliberately no third rung, because ACP gives no way to nudge a turn in flight and a second `session/prompt` kills the running turn and reads as prompt injection on two of three harnesses (M0-4). Only `ttlMs` acts, and all it does is ask `core/run.ts` to cancel that one task. Every knob is disabled at `0`. **The module owns no timer and no agent** — `sweep()` is called by `core/run.ts`'s interval and `now` is injectable, which is what lets an hour-long TTL be tested by moving a number. Repeat counts `tool_call` only, never `tool_call_update`, or one slow tool would read as a loop; the streak (and its warning) reset when the title changes. A hook that throws is swallowed per task, so one broken consumer cannot leave the tasks behind it unchecked. The three limits are run-file keys at **both** levels, task wins — `Task` carries them structurally, so `core/run.ts` hands a `Task` straight to `watch()`.
- **`core/notify.ts`** — the attention signal (M1c-4). One bus listener, subscribed by `cli.ts` on **both** paths, for the two events a human needs while looking elsewhere: `_client_permission_pending` and `_client_stall_warning`. Bell, one stderr line, and a desktop notification that is **spawned and forgotten** — no presence check, because probing for `notify-send`/`osascript` costs a lookup per event to learn what the failing spawn reports for free, and a missing notifier must never change an exit code. It owns the stall line outright: `cli.ts` used to print that from a subscriber of its own, and two subscribers on one event is how a run says it twice. It also filters on `kind`: `_client_permission_pending` fires before *every* policy await, but `makeAskPolicy` returns on `READ_ONLY_KINDS` without reaching readline, so a `read`/`search`/`fetch`/`think` decision is over before anyone could look up — the notifier imports that same set from `core/policy.ts` rather than restating it, so the two cannot drift. `write` and `notify` are injectable, which is what lets the suite assert the decision without a real bell or a real subprocess.
- **`core/permissions.ts`** — the pending-decision queue (M2-3, #33). `policyFor(runId, bus, signal)` is one run's `ask` decider: `READ_ONLY_KINDS` pass unasked, as `makeAskPolicy` does, and every other kind waits as one entry until `answer(id, allow)`, the timeout (deny) or the run's signal (deny). `denyTask(runId, taskId)` is the third denier, for the task the watchdog's TTL cut while its siblings keep the run alive: `daemon.ts` calls it off `_client_task_finished` rather than off the cancel, because a dying harness sends one more `session/request_permission` on its way out. **First writer wins**: an entry settles once and a later answer reads `settled`, which `daemon.ts` sends as 409. The answer is a boolean, never an option id, so `pickOption` stays the only place that picks and #13's `allow_always` guard is untouched. Settled ids are kept for the daemon's lifetime (`ponytail:`, until M2-6 gives runs one).
- **`schema/run.schema.json`** — an authoring aid an editor reads. **Never a second validator**: `validateRun` cannot be replaced by a schema that fills no defaults, reaches no registry and spots no duplicate id, and checking one at runtime would cost a dependency. One test asserts its property names equal `RUN_KEYS` and `TASK_KEYS`, which is the only thing keeping the copy honest.
- **`daemon.ts`** — the HTTP transport over `core/` (M2-1, #31), on `node:http` and bound to `127.0.0.1`. **One daemon for all of the operator's repositories**: `POST /repos` adds one (`GET /repos` lists them), and `POST /runs {cwd, run}` refuses a folder outside every added repository with a 403, so there is one port, one token and one dashboard while run state stays in each repository's `.kapelle/`. `POST /repos` runs `checkStateDir`, so a tracked or unignored `.kapelle/` is a 409 before any run. `POST /runs` answers in a fixed order — not added (403), then `.kapelle/` unsafe (409), then an invalid run (400), then a dirty tree (409) — and membership comes first on purpose: it resolves the root with `stateDirRoot`, which never throws, so an unadded repository is told to add itself rather than to fix a `.kapelle/` it has no reason to have. **Every request needs the bearer token, loopback included** — every account on the machine reaches `127.0.0.1`, and a run file is a command line. The token is 32 random bytes, compared as sha256 digests with `timingSafeEqual`, and lives with the port and pid in `$XDG_RUNTIME_DIR/kapelle/daemon.json` (a per-user temp dir where that is unset): outside every repository, in a directory the daemon refuses unless it is yours and `0700`, written `0600`, and published only once the port is open. **That file is the single-instance lock**: written under a private name and `link`ed in with the pid already in it, so a second daemon finds a live pid and exits without touching it; a dead pid's file is replaced under a `daemon.json.lock` directory, so two daemons starting in the same instant cannot both replace it (M2-4). **Lifecycle (M2-4, #34):** SIGTERM and SIGINT cancel every run, wait for each to settle — which waits on its harness — remove `daemon.json` and exit 0, with no kill loop of its own. Live harness pids are mirrored to `children.json` beside it from the `_client_harness_*` events, removed once none is live, so a file left after a crash names what was running for M2-5. `core/runtime.ts` owns the directory, because `kapelle daemon add <path>` reads the token too; `kapelle daemon start` imports `daemon.ts` and runs in the foreground. It calls `stateDirRoot`, `checkStateDir`, `validateRun`, `openWorktrees`, `runRun` and the permission queue, and nothing below them — no `resolvePolicy`, no `AcpAgent`, no `acquire` — so the scheduler stays testable without a server. `openWorktrees` runs in the handler as a read-only preflight, so a dirty tree is a **409 before any run exists**; `runRun` repeats it. **`ask` runs over the API (M2-3, #33)**: each run gets `core/permissions.ts`'s queue as its `askPolicy`, `GET /permissions` lists what is pending across every run, and `POST /permissions/:id {"allow": boolean}` answers — 200 the first time, 409 once settled, 404 for an id never issued. An unanswered decision is denied after `--permission-timeout` (120 s), and cancelling a run, or the run ending, denies what it still has open. `DELETE` is asynchronous (202 with `cancelRequested`, the verdict on `GET`), because `core/run.ts` already stops a harness 2 s after the abort. `GET /runs/:id/events` (M2-2) is SSE over `core/eventlog.ts`: `id:` is the `seq`, `Last-Event-ID` resumes after it (400 outside `0..size`), and the stream ends when the run does. `runRun` hands the log over through `RunOptions.onEventLog`; a request that arrives first waits on it rather than 404ing a run that exists. Runs live in memory until M2-6, and every notice goes on the run record, since there is no terminal for #13's lines to survive on.
- **`cli.ts`** — single-agent CLI, hand-rolled arg parsing, SIGINT → `session/cancel` then 2s grace before `stop()`, and exit once the harness is gone. `--file <run.json>` is the other half: N tasks through `core/run.ts`, prose buffered per task, milestones live. `--agent`, `--cmd` and `--mode` are **refused** alongside `--file`, because the run file already answered those per task; and `ask` in a run file survives for **exactly one asker** — `makeAskPolicy` owns a single readline over one stdin, so two tasks prompting at once would interleave two questions and mis-attribute an answer. One asker plus a TTY keeps `ask`; anything else re-resolves every asking task as `safe`. M2-3's queue serves N askers in the daemon only (decided 2026-09-16, #33); M2-9's `attach` is what lifts the CLI's limit, which is why `core/run.ts` takes the decider as `RunOptions.askPolicy` and never builds one.

### Two client invariants worth preserving

**Permission decisions depend on state carried across messages.** `session/request_permission` may arrive with only a `toolCallId`. Title and kind were announced earlier in the `tool_call` notification, so `AcpAgent` maintains a `toolCallId → {title, kind, rawInput}` map. Break that bookkeeping and every policy decision goes blind.

**The policy filters what a harness asks, and the one mutation it can perform through us — it is not a sandbox.** One file, `core/policy.ts`, applied identically to every harness. `safePolicy` allows only the `READ_ONLY_KINDS` set (`read`, `search`, `fetch`, `think`); `makeAskPolicy` auto-approves those and prompts per mutation; `auto` approves all — reach them through `policyFor(mode)`, which is the only map from a mode to a decider. What the filter can reach is per-harness — opencode never asks, and copilot's behaviour changed across builds — so per-harness containment lives in the registry, not in this sentence (`docs/M0-FINDINGS.md` §M0-1). `#guardPath` rejects any `fs/*` path outside the workspace root — comparing **realpaths** since M1b-6, because `resolve` is string arithmetic and a symlink inside the root pointing out of it used to read as in-root. Since M1b-6 `fs/write_text_file` also goes through the policy (`#guardWrite`) when no `session/request_permission` has already decided that exact path, which is the whole of "mutation without asking": without it `safe` refuses the *request* to edit and then performs the edit for any harness that skips the request and calls the file service directly. A write that follows an approved permission for the same path reuses that decision, so `ask` does not prompt twice for one edit. **An approval covers exactly one write and is consumed by it**, `allow_always` included: `pickOption` prefers `allow_once` and reaches `allow_always` only when the harness offered nothing narrower, so keeping it would be a session-long grant for a path nobody chose to grant that way. A *denial* is the sticky entry, so a harness that writes after being refused is refused again without re-asking. It is the only mutation the client can see on the wire; one made through the harness's own shell stays outside the policy's reach and is inferred afterwards by `policyNeverFired`. Both bound this client's own file service, not the agent, and no surveyed harness calls `fs/*` at all. Keep the two layers separate: policy is about intent, the path guard is unconditional and applies under `--mode auto` too.

**`safe` negotiates before it filters (M1a-5).** `negotiateSafeMode` sends `session/set_mode` with the registry's `measured.modeMap.safe` right after `session/new`, and that is the only half that reaches opencode, which never asks anything: measured, it wrote the file without negotiation and declined with it. Skipped for a harness with no `measured` half, because the ids would be a guess; skipped for a measured harness with no `modeMap` (pi-acp, whose ACP modes are thinking-effort levels, not safety modes); and skipped for `ask` and `auto`, because sending `auto`'s id would put claude into `bypassPermissions`. A skip or a failure prints a notice and continues — it never fails the run. The refusal arrives as agent prose, so this is defence in depth, not enforcement.

**Mode and `allowReadOutsideRoot` resolve in one place.** `resolvePolicy` settles `task > run > harness > default`. A mode above the entry's `maxMode` is a validation error naming both values, never a silent downgrade, and `safe` forces `allowReadOutsideRoot` to `false` however it was asked for. `ask` without a TTY re-resolves as `safe` rather than renaming itself, so `safe`'s own rules apply to what actually runs.

**A permission answer never guesses.** `pickOption` returns `null` when no option matches the decision, and the client answers the protocol's `cancelled` outcome. The old tail returned `options[0]`, which fails open — claude lists `allow_always` first, so a denial would have become a persisted grant (measured 2026-09-02, issue #13).

### Synthetic events

This layer emits twelve synthetic events of its own, not defined by the protocol: `_client_permission`, `_client_wrote_file` and `_client_cancel_requested` (M1a-3, #62 R4 — recorded at the moment `session/cancel` is sent, because copilot answers `end_turn` for a turn it cancelled, so our own record of having asked is the authoritative term for M1b-2), plus `_client_result_warning` (M1b-4, emitted by `core/run.ts` when a result cross-check disagrees), `_client_stall_warning` (M1c-1, emitted by `core/run.ts` when the watchdog's idle or repeat rung fires) and `_client_permission_pending` (M1c-4, emitted by `protocol/agent.ts` immediately **before** each policy await), `_client_harness_spawned` and `_client_harness_exited` (M2-4, emitted by `protocol/agent.ts` with the subprocess pid; `daemon.ts` keeps `children.json` from them, and nothing renders them), the three task boundaries `_client_task_started`, `_client_worktree_created` and `_client_task_finished` (M2-2, emitted by `core/run.ts` for the persisted log; a task cancelled before it started gets a `finished` with no `started`), and `_client_permission_queued` (M2-3, emitted by `core/permissions.ts` with the id `POST /permissions/:id` answers, so a stream reader need not poll; nothing renders it). `render.ts` draws the first two; the third is capture-only; the fourth is printed by `cli.ts`'s `--quiet` subscriber and is available to later bus consumers. `_client_stall_warning` and `_client_permission_pending` are the attention pair, and **`core/notify.ts` is the only subscriber that prints them** — a bell, one stderr line, and a best-effort `notify-send`/`osascript`, in **both** modes, because a stall warning is only useful while the task is still stalled and an unanswered prompt stalls the run outright. `_client_permission_pending` fires in every mode — `AcpAgent` holds a `Policy`, not a `ClientMode`, and teaching it one would put a run-layer concept in the protocol layer — so the **consumer** filters, on two axes: `makeNotifier({asks, askIds})` is armed only where a human can actually be blocked, and it drops `READ_ONLY_KINDS` even there, because `ask` auto-approves those without prompting. On the single-agent path that is `resolved.mode === "ask"`; on the `--file` path the run passes `asks: canAsk` plus the one surviving asker's task id, so `safe`/`auto` tasks in a mixed run do not ring. It is deliberately not drawn by `render.ts`: under `ask` the prompt is already on screen, and under `safe`/`auto` the decision is instant, so drawing it would announce a wait that never happened. The render switch has no `default`, so an unrendered variant is ignored rather than drawn incorrectly. Prefix any new synthetic event with `_client_` so it stays distinguishable from real `sessionUpdate` values.
