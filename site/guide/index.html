Guide

Everything a new kapellmeister needs: install, your first room, your first loop, and every command. Read it top to bottom once, then come back to the part you need.

PRIVATE PREVIEW

The npm package is not out yet. It is coming soon. Until then, people with access to the repository install from source.

1Install

You need Node 24 or newer, git, and macOS or Linux. WSL counts as Linux. Windows is not supported.

npm · coming soon$ npm install -g kapelle
$ kapelle --help
pnpm · coming soon$ pnpm add -g kapelle
$ kapelle --help
bun · coming soon$ bun add -g kapelle
$ kapelle --help
from source · needs repository access$ git clone https://github.com/EdwardLiuyc/kapelle.git
$ cd kapelle
$ npm install
$ npm link           # puts kapelle on your PATH
$ kapelle --help

From source, npm unlink -g kapelle undoes the link. If npm link fails with EACCES, npm's global folder belongs to root. Use a folder you own instead of sudo:

$ npm config set prefix ~/.local    # then add ~/.local/bin to PATH

From source, you can check kapelle with no agent and no account. A fake agent ships with the repository:

$ npm run selftest

You should see ✓ allowed Write ACP_TEST.md. Delete ACP_TEST.md when you are done.

2Quick start

kapelle is the client. The agent is a separate program, and it logs in by itself. pi is the default. Install pi and its ACP adapter, then log in to pi once:

$ npm i -g @earendil-works/pi-coding-agent pi-acp
$ pi                   # type /login, then quit

Now type kapelle inside any repository. It starts the daemon when none runs, and opens the chat:

$ kapelle

Or send one prompt, with no chat:

$ kapelle "summarise this repo in three sentences"
READ THIS FIRST

pi works in your own checkout here, and it never asks for permission, so no mode can stop its changes. Read What a mode cannot stop before you give it real work.

Useful options:

  • --agent <id> picks another agent. See Supported agents.
  • --cwd <dir> works in another folder.
  • --mode safe|ask|auto sets what the agent may do. See Modes.
  • --verbose shows the agent's own error output.
  • --quiet hides normal output, but never the safety notices.

3Set up your agents

At the first start, the chat shows the setup list: each agent the daemon finds on its PATH, and what is missing. It shows again at each start until you choose done, and always while no agent is ready. /setup opens it at any time. kapelle setup prints it.

$ kapelle setup
pi      ready (pi 0.74.0, pi-acp 0.0.34)
codex   codex 0.51.0; needs codex-acp: npm i -g @agentclientprotocol/codex-acp@2.2.2
kimi    not installed: no kimi on the daemon's PATH
  • Install an adapter. When an agent is there but its ACP adapter is not, check it in the list and choose setup. The daemon runs npm i -g with the version kapelle was tested on. If npm fails, for example because it needs sudo, the list shows the command for you to run.
  • The login check. kapelle opens a session with each ready agent, with no prompt, so it spends no tokens. It saves the agent's models and whether it is logged in. A logged-out agent shows its own login command. kapelle never logs in for you.
  • Pick a model. /new and /add take --model <id>, and their form lists the saved models. If the agent refuses the model, it keeps its own, and a notice says so.

4Rooms, loops, runs

Six words cover all of kapelle:

agent
A coding agent such as pi, Claude Code or Copilot. It runs as a separate program. kapelle talks to it with ACP, the Agent Client Protocol.
daemon
One background program that holds all your work, for all your repositories. Close the terminal, and the work stays.
room
A long chat with a team of agents. Each agent keeps its memory across messages. You decide who does what by choosing who to message.
loop
A room with a lead agent, the orchestrator. It follows a recipe you wrote, gives the work to the others, and stops for every choice.
run
Many tasks at once, from one file. Each task has its own prompt, agent and mode, and ends with a result.
worktree
A separate checkout of your repository. Each agent in a room, and each task in a run, gets its own, on its own branch. Your own checkout stays yours.

Open a room

Rooms live in the daemon. kapelle alone starts it in the background when none runs. It keeps running after you leave the chat. Add each repository once:

$ kapelle                  # the chat; starts the daemon if needed
$ kapelle daemon add .     # in your repository, once
$ kapelle daemon stop      # when you want it gone

Then open a room:

$ kapelle chat new --agent pi     # open a room and chat in it
$ kapelle chat                    # every room, on a terminal
$ kapelle chat list               # every room, as text
$ kapelle chat attach <roomId>     # rejoin a room; its history replays
$ kapelle chat dismiss <roomId>    # stop the room's agents

Each agent in a room works on its own branch, kapelle/<roomId>/<agentId>.

A new checkout has none of your untracked folders, such as node_modules. List them as linkPaths in your repository's file, and each new checkout links them from yours.

The room API is new, and it can still change.

Talk to agents

Type a message and press Enter. It goes to the room's orchestrator: the agent whose role is orchestrator. In a room with no orchestrator and one agent, it goes to that agent. Start a message with @name to send it to that agent instead. In an agent's thread, the box always starts with its @name.

An agent works on one message at a time. A message to a busy agent waits in a queue.

Add a second agent with /add. For example, a reviewer on pi that may only read:

/add pi --name rev --mode safe

Then talk to it by name:

@rev review the last commit on dev's branch

Room commands

A command never reaches an agent. Room commands work in any view. An agent's command needs its @name first.

CommandWhat it does
/leaveExit. The rooms and their agents stay alive.
/dismissStop the room's agents. Uncommitted work stays in each agent's checkout.
/deleteShow every branch the room owns and its unmerged commits, then ask again. Yes removes the room and its branches.
/helpShow the commands on the screen.
/setupOpen the setup list.
/new [agent]Open a new room. Options: --cmd, --name, --model, --title, --cwd.
/add <agent>Add an agent to the room. Options: --cmd, --name, --role, --mode, --model, --base @name|ref.
/loop <recipe> <task> ["note"]Start a loop in a new room. Options: --agent, --cmd, --cwd.
/title <new title>Rename the room.
@name /mode <m>Set the agent's mode: ask, safe or auto.
@name /role <r>Set the agent's role, or none.
@name /rename <new>Rename the agent.
@name /cancelCancel the agent's turn.
@name /removeRemove the agent from the room.

/new or /add alone opens a form.

Keys and marks

On a terminal, a sidebar lists every room and its agents.

Take the work

In a room, kapelle never commits for an agent. An agent commits its own branch. Uncommitted work stays in the agent's checkout.

  • See an agent's changes: ctrl+o, then view changes. The side pane shows the diff. b switches between uncommitted changes and the whole branch.
  • Give one agent another's work: ctrl+o, then fast-forward from …. The pane shows what it would bring, and Enter confirms.
  • Take the work into your own checkout with git, when you are ready.
$ git log -p kapelle/<roomId>/<agentId>
$ git merge kapelle/<roomId>/<agentId>

Run files

A run hands out many tasks at once. Each task has its own prompt, agent and mode, and each ends with a result.

{
  "agent": "pi",
  "mode": "safe",
  "tasks": [
    { "id": "summarise", "prompt": "Summarise what this project does in three sentences." },
    { "id": "look-for-bugs", "prompt": "List any obvious bugs or missing error handling you can see." }
  ]
}
$ kapelle run --file tasks.json

In a git repository, each task gets its own worktree, on a branch named kapelle/<runId>/<taskId>. Keep working in your own checkout while the agents work in theirs. Your uncommitted changes do not reach the tasks, and kapelle tells you so. Outside a git repository, the tasks share the folder.

When a task ends done or warned, kapelle commits its work on the task's branch. Task ids name git branches, so kapelle checks them and never changes them.

In the background

With the daemon running, hand the run over and follow it from any terminal:

$ kapelle run --file tasks.json --detach   # prints the run id
$ kapelle ps                               # every run and each task's status
$ kapelle attach <runId>                    # watch it, and answer its ask prompts
$ kapelle attach <runId> --task <taskId>    # watch one task in full

kapelle rings the bell and sends a desktop notification when a run needs you.

Merge the results

$ kapelle merge <runId> --squash

This puts the changes of all tasks into your working tree, unstaged. It makes no commit. It refuses when two tasks change the same file, or when your own changes touch a file a task changed.

Look at one task's work first with git log -p kapelle/<runId>/<taskId>.

Where the work lives

Worktrees and records live in ~/.local/state/kapelle/. Nothing goes into your repository.

$ kapelle workspace                    # where this repository's work lives
$ kapelle workspace move <old> <new>   # after you move or rename the repository

Use workspace move, not a plain mv. A plain mv breaks git's link to each worktree.

Run a loop

Most issues run the same loop: pick up, build, review, open the PR, answer the bot reviews, hand over. A loop gives it to one agent, the orchestrator. It adds the other agents when their step comes, gives them the work, reads their reports, and decides the next step. It does none of the work itself, and you decide every choice.

The daemon must run, and the repository must be added. Then start a loop with a recipe and a task:

$ kapelle loop list                              # every recipe, and which one wins a name
$ kapelle loop fix-issue 312                     # recipe fix-issue, task 312
$ kapelle loop fix-issue 312 "skip rev2"          # a note for this run only
$ kapelle loop fix-issue 312 --agent pi          # a pi lead; claude by default

In the chat, /loop fix-issue 312 does the same. kapelle opens a room titled fix-issue-312 and adds the lead, po, in auto mode. Its first message holds kapelle's orchestrator skill, your recipe, the task and the note, so you see all it was told.

  1. The plan. po joins the recipe, the task and the note into one plan: the team, the steps, the outside review and the protected paths. It does no work before you say go. A plan you correct costs nothing.
  2. The work. po sends one order at a time and ends its turn. Its status line says which step runs.
  3. The stops. po ends its turn with a question for you: one line on where the loop is, the options, a recommendation, and the reply that lets it go on.
  4. The hand-over. The last report says what each step did, the open findings, and the number of commits. You read the work and merge it.

You may talk to any agent at any time. Answer a choice to po, or to the worker that raised it. Cancel a turn with @name /cancel. po then waits for you, and does not send the order again.

What the lead does

Orders through kapelle
po talks to the others only with kapelle room, from its own checkout. Each order shows in your timeline as po → dev. A worker never gives orders to another worker: the daemon refuses it.
A reply to the sender
When a worker's turn ends, its answer goes back to po as a message, [reply from dev]. When you talk to one of its workers yourself, po gets a copy of your message and the answer.
The step board
The main developer ends every report with the plan's steps, each marked done, running or not started. po reads where the loop is from the board, and never guesses.
Reviews in a line
A reviewer starts from the developer's branch and commits its fixes. po moves them in with a fast-forward, removes the reviewer, and tells the developer which commits came in. The developer judges each fix.
Every choice is yours
po stops for every choice, a protected path, a step that fails twice, an agent that exited, an outside review that times out, a refusal it cannot fix, and the hand-over.
A hard limit on rounds
An outside review, such as a bot on the PR, gets 3 rounds unless the recipe says other. A round with only nits ends the review. At the limit, po offers: hand over as it is, fix without another review, or split the task.
THE SKILL IS A PROMISE, NOT A WALL

po runs in auto. The skill tells it to edit, build, commit and push nothing, but no mode can hold it to that. Its workers run as your user, with your forge login. A stop button, a cap on the turns po gives out, a bell when it waits for you, and a decision log are coming soon.

Write a recipe

A recipe is a Markdown file in your own words. kapelle never reads it: it pastes it into po's first message. So there is no format and no validator. kapelle looks in two folders, and for one name the first wins:

  • .kapelle/loops/<name>.md in your repository, to share with your team;
  • ~/.config/kapelle/loops/<name>.md, your own, for every repository.

Give it these parts:

The team
Each worker's name, agent and role, and when it joins. Say which one is the main developer.
The steps
In order, with the skill or the words each one uses.
The outside review
Optional. How to start it, how a worker waits for it, and the most rounds.
Protected paths
Optional. Paths that need your yes before a worker changes them.
Rules for every worker
For example, what git may do in this loop.

A short example:

# fix-issue

One GitHub issue: pick it up, build it, review it, open the PR,
answer the bot, hand over. The task is the issue number.

## The team

| Name | Harness | Role | Joins |
| --- | --- | --- | --- |
| dev | claude | developer, the main developer | at the start |
| rev1 | pi | reviewer | after dev commits, from dev's branch |

## The steps

1. Pick up. dev runs /pickup-issue for the issue.
2. Build. After "go": dev builds it, runs the tests, and commits.
3. Review. rev1 reviews dev's branch and commits its fixes.
4. PR. dev pushes and opens the PR.
5. Outside review. Below.
6. Hand over.

## The outside review

dev comments "@claude review" on the PR and waits for the answer
inside its own turn, 20 minutes at most. 3 rounds at most.

## Rules for every worker

- Commit and push only your own branch. Never merge.

kapelle's own repository runs its issues with a longer one: .kapelle/loops/fix-issue.md.

The setup list shows which ones the daemon finds, and can install a missing adapter for you. Any other ACP agent works too: --cmd "some-agent --acp". kapelle says that it is not tested.

Claude Code has no ACP mode of its own, so it needs the adapter above. If you see spawn claude-agent-acp ENOENT, the adapter is not on your PATH. Check with command -v claude-agent-acp. You can run kapelle from inside a Claude Code session.

Modes: safe, ask, auto

ModeWhat it does
safeAllows reads. Refuses every change the agent asks about.
askAllows reads. Asks you about each change. A run in your terminal needs the terminal: without one, kapelle uses safe and prints a notice. A room, or a run started with --detach, asks through the daemon: the question waits for your answer, and is refused at the time limit.
autoAllows everything. A file request for a path outside the workspace is still refused.

In a room, each agent has its own mode. The default is auto, because a room is often left alone, and an ask default would leave it waiting.

In the question box, each answer has a number. Deny comes first, so a stray Enter says no. A key only moves the cursor, and only Enter answers.

What a mode cannot stop

A MODE IS A FILTER, NOT A SANDBOX

A mode decides the answer when an agent asks for permission. An agent that changes files through its own shell does not ask. pi never asks. opencode asks only for a write outside the workspace. So safe does not stop them.

kapelle always refuses a file request for a path outside the workspace, in every mode. But this covers only file requests that go through kapelle. An agent can still write the file itself: opencode 2.0.18 did, after kapelle refused its request.

kapelle prints a notice about this, and --quiet never hides it. If you need a wall, run the agent in a container.

Configuration

Two optional JSON files, and KAPELLE_* environment variables. Nothing creates the files for you. Both are strict: an unknown key or a wrong type is refused, and the error names the file and the key.

Your user file

~/.config/kapelle/config.json holds the daemon's settings:

{ "port": 4719, "permissionTimeoutMs": 120000 }

Your repository's file

.kapelle/config.json in your repository holds the run defaults, and the paths each new checkout links. It is the only file kapelle reads from your repository. You may commit it.

KeyWhat it sets
stallIdleMsWarn when an agent shows no progress for this long. 0 turns it off.
stallRepeatCountWarn when an agent repeats the same step this many times. 0 turns it off.
ttlMsCancel a run's task after this long. 0 turns it off.
maxConcurrencyHow many tasks of a run work at once.
retentionMsHow long finished runs and dismissed rooms are kept.
linkPathsPaths, such as ["node_modules"], that each new checkout links from your own. Git must ignore each one.

A linked path is shared, not a copy: an agent that writes through it writes your file. List only paths the agents read.

A KAPELLE_* variable overrides both files. linkPaths has none. A value in a run file still wins over all of them.

Troubleshooting

An agent fails to start

It often shows as Internal error (code -32603). Run again with --verbose to see the agent's own error output. In a run, read the task's .stderr.log file in the run's record folder. kapelle workspace tells you where that is.

spawn claude-agent-acp ENOENT

The Claude Code adapter is not on your PATH. Install it, then check with command -v claude-agent-acp.

--mode ask became safe

ask in a plain run needs a terminal to ask you in. Without one, kapelle uses safe and says so. Use --detach to answer through the daemon instead.

add the repository first

The daemon does not know this repository yet. Run kapelle daemon add . in it once.

Worktrees show as prunable

The repository was moved with a plain mv. Run kapelle workspace move <old> <new> to repair the links.
